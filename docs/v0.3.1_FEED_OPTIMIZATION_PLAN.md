# v0.3.1 Feed 性能优化计划

日期：2026-10-02。经过 grilling 确认后授权实施；按阶段测试，不提交 Git，不迁移数据库，不改变 Label、模型、来源配额、质量闸门和曝光规则。

## 已确认的行为

- 新版全部入口采用 Ready-first；经典首页保留推荐与耗尽回退行为。
- Ready 使用候选保留期限、完整详情、当前入口规则、实时过滤/历史/冷却/质量和原 Mixer 判断，不能只数 complete；不新增可评分门槛。
- 普通全部推荐和独立热门/探索不足时立即返回部分页，后台补池；通过手动换批恢复，不改写缓存页。
- 具体分区新批次首屏不足时最多一个相关种子召回、min(缺口,2)次详情发送尝试；recent/discover不触发此例外。
- 关注新批次首屏取最新 head，不同步回溯旧 offset；最多 min(最新缺口,3)次详情发送尝试，只返回已完整的最新前缀。失败使用本地时间线并提示缓存降级。
- 新 stream 首屏网络例外共用5秒软预算，涵盖排队、依赖、重试退避；到期停止未发送任务，不承诺在途请求立即中断。
- 发送尝试包含 nav、初发、重试和重定向；统一一秒间隔，同级 FIFO，连续三次前台后允许一次可发送的后台。
- 低于两页真实成页能力唤醒后台，目标三页；来源按配额和让位维护，独立入口按自身需求。最多八项近期需求，十分钟失效；每轮最多12次详情、3次召回发送尝试，无进展不忙循环。
- 每 stream 串行生成，短全局锁保护创建/实验分组以及最终重查、选择和事务提交；网络/节流在锁外，已有缓存页绕过生成锁。
- 页面、记录、模型和来源设置保持幂等；当前硬屏蔽仍对缓存页生效。has_more依据当前可用后续内容，不承诺后台未来一定补出内容。

## 阶段与验证

0. 只读审计及保存基线。
1. Ready/Mixer预判和Cache-first；完整池及让位成页零网络。
2. 缺口补全、关注最新前缀、分区预算、发送计数和短页降级。
3. 后台低水位、需求合并、唤醒及失败停机。
4. 缓存快路径、每stream协调、短全局提交锁和并发幂等。
5. 发送层优先队列、公平性、重试/重定向/取消/退避。
6. 全量回归、前端受控验证和同条件至少50样本性能对比。

每阶段独立修改、测试、性能对比，通过后继续；仅回退该阶段改动，保留既有未提交工作。

全量测试使用 `test*.py`，包括原73项覆盖；修正原固定12次detail及证明缓存等待长锁的旧断言，新增真实缺口、最新前缀、并发、发送层和后台测试。

无须网络新页：p50<500ms、p95≤1s；缓存页竞争场景p95≤200ms；关注/分区网络例外另报必要原因、尝试数和预算，不套用零网络目标。默认不开深度诊断；仅优化后非网络耗时仍明显>1s时再启用。

## 四类结论

A必须执行：Cache-first、缺口补全、缓存快路径、每stream协调、短全局锁、低水位和前台优先级。

B建议执行：短页率、补池失败率和来源分布的短周期观察。

C有数据后决定：跨请求快照、索引/批量DB优化、第二层诊断。

D本轮不执行：降低节流、取消退避或质量要求、提高原生比例、重写Ranker/Mixer、数据库迁移、重新训练、前端重构。
