# v0.3.1 Feed 性能诊断：第一轮

日期：2026-10-01。结论：主要问题已由第一层埋点定位，不开启第二层逐条 SQL／JSON 深度采样。本轮交付诊断与测试，尚未修改正式召回策略或缩小锁范围。

## 1. 最大延迟来源

**主要阶段是同步补详情：两批真实请求分别耗时 12.00 秒、11.95 秒，均尝试并发出了 12 次 detail 网络请求。**

按来源划分，related 是第一大来源：8.525 秒、8.284 秒；follow 是第二大来源：7.710 秒、6.023 秒。up_archive 为约 8.6 毫秒，rcmd 为约 6.8～7.2 毫秒，hot 为约 12.5～13.4 毫秒。来源时间包含各自的读取、召回、补详情和排序，不能与阶段时间再次相加。

从互不重复的等待／执行原因看，**第一是主动节流 sleep（11.33 秒、10.02 秒），第二是 Bilibili HTTP 执行（4.52 秒、3.95 秒）**。两项合计占总耗时约 96.8%／96.7%。这里不是建议取消一秒节流：应减少放在前台关键路径上的请求。

## 2. 第二大延迟阶段

**同步召回为第二大阶段：4.249 秒、2.364 秒。**第一批包含关注动态刷新和三个 related 种子扩展；第二批仅 related 扩展仍要 2.364 秒。

保存明细的两批真实新页总耗时为 **16.372 秒、14.448 秒**；应用层 API 调用为 17／15 次，其中 detail 均为 12 次。活动模型为 `baseline-v02-f6309d9ab2a7cb2e`，已预热；rank 为 15.4／20.6 毫秒，mixer 为 0.059／0.063 毫秒。当前慢请求的主因不是排序或混合。

本轮没有以毫秒级 rank 结果推断未启用的 v0.3 候选排序器性能，也不把两批数据描述为稳定 p95／p99。

## 3. 热缓存为什么仍慢

必须区分“候选池已热”与“同一个生成页已缓存”。

- 请求前已有完整候选：第一批 follow 30 条、up_archive 58 条、related 308 条，另有 hot 36 条、rcmd 33 条。仍存在大量原始列表条目未补详情，related 共 1710 条。
- `_generate_mixed()` 对新 stream 的第一页无条件尝试 related 扩展，即使已有足够的完整候选。
- 接着无条件调用 `pool.complete(..., budget=12)`，从未补全队列中补详情，而没有先按当前页可用内容／来源缺口判断是否需要等待；本次每批 follow 和 related 各补 6 条。
- 同一生成页重读只需 **8.477／8.544 毫秒**，API 与 detail 网络请求均为 0。因此缓存本身能快，问题发生在“生成新批次”的路径。

做了一个针对原因的对照：在同一生产数据库的临时副本中，只临时跳过同步 expand／complete，保持正式过滤、质量闸门、冷却、排序和混合，**仍返回 12 条，耗时 128.075 毫秒，API 和 detail 均为 0**。

这证明现有完整候选足以生成页面，前台不必为填满当前页等待上述全部请求。此对照会影响新鲜度与候选选择，不是已经应用的正式优化，也不保证返回相同 BV；推荐策略应另行明确“先用缓存、后台更新”的规则。

## 4. 前台是否被后台或其他 Feed 请求阻塞

**其他 Feed：已确认。**`_page()` 在 `_gen_lock` 内生成整页，网络请求和限速 sleep 也在持锁期间执行；`refresh()` 同样需要该锁。

受控并发回放中，新页生成耗时 7.394 秒；另一已缓存页耗时 7.148 秒，其中 **7.138 秒是等待 `_gen_lock`**。缓存页没有发任何 API，也没有打分或混合。这是队首阻塞的直接证据；回放的绝对耗时受临时库文件 I/O 和并行回归影响，不替代真实网络延迟。

**后台共享节流器：能够阻塞前台，但本轮真实样本未测在线后台占比。**前台与 scheduler／历史同步都经过 `bili._lock`；后台节流 sleep 在锁内，前台会排队。使用假 HTTP 的受控后台槽测试，后台持有约 80 毫秒时，前台实际等待该锁约 80 毫秒，总请求约 83.3 毫秒。该测试证明机制，不代表线上每批都等待这么久。

真实采样为隔离原因而未启动后台线程，生成锁等待仅约 0.006 毫秒，节流锁排队约 0.04～0.05 毫秒；10～11 秒主要是请求自身的节流 sleep。不能把它们归因为后台占用。

**scheduler 工作锁不是此次阻塞点。**`tick()` 使用非阻塞获取；锁忙时跳过。测试确认 busy 计数增加，而 `waited_source_scheduler_lock=false`。来源池锁同样非阻塞。后台影响前台的路径是共享节流器／资源竞争，不是前台直接等待 scheduler 工作锁。

## 5. 是否存在不必要的同步 Bilibili 请求

**已确认存在“对当前页成页非必要”的同步请求。**热候选新页仍扩展三个 related 种子并补 12 条详情；缓存对照在不发这些请求的情况下仍完整成页。

优先级建议：

1. 完整可用候选足够时，先生成当前页，将 related 新鲜度更新和额外详情交给后台；分区切换的实时扩展约定需要保留。
2. 同步详情预算按来源缺口决定，最多 12 不应变成每批都尽量补 12。详情完整、屏蔽、陌生 UP 闸门仍须严格执行。
3. 缩小 `_gen_lock` 的网络持锁范围，或以 stream/page 协调；保持 stream 快照、分组、重试幂等和一次记录，不能简单删除锁。
4. 再考虑前台请求优先于后台补缓冲，保留全局一秒节流及风控退避。

rank／mixer 优化和逐 SQL 调优暂不进入第一优先级；现有关键路径中非网络／节流部分约 0.5 秒，主因已明确，不需要为定位继续开启深度采样。

## 方法、数据与限制

- 真实请求使用现有登录态，保持一秒节流；Feed 和设置写入 SQLite 临时副本，后台关闭、活动模型预热。未改生产候选、反馈、曝光、模型或来源设置，未激活排序器。
- 首次真实采样三批观察到 14.43～16.46 秒，但清理时暴露 Windows SQLite 连接未关闭问题，明细未成功保存。脚本改用显式关闭连接，随后仅复采两批保存完整明细；报告定量分解基于后两批。
- 本地回放有 10 次 warm-refresh、10 次详情冷池、10 次缓存重读，以及新页／缓存页并发和后台资源竞争。第一次回放日志中的 `cached-page` 实际是第二次新 view 生成，以 `feed_page_cache_hit=false` 为准；脚本已将后续名称修正为 `second-refresh`。`cached-page-repeat` 才是真正缓存重读。
- 第一层输出 total、来源阶段、HTTP／detail、节流、生成锁、缓存页分支、rank／mixer 和父子 span。逐条 SQLite、JSON 解码、真实插入／更新细数及候选命中比例保持未测（null），不是 0；第二层开关默认关闭。
- CLI 测量入口是服务调用，`total_ms` 包括这些服务操作，但不含 Flask 序列化和浏览器渲染。正式 HTTP 埋点从 Flask 请求到响应构造结束计时，并给出 `X-Feed-Trace-Id`；两种入口不可混为一个统计口径。
- 未运行完整冷启动、线上后台占比、所有分区或一周大样本，这是按第一轮目标主动收窄，不影响以上原因定位。

原始数据与 CSV 位于项目忽略目录，不加入 Git：

```text
.tmp/feed-performance/real/         两批真实新页 + 两次缓存重读
.tmp/feed-performance/cache-only/   仅缓存成页对照，无外网请求
.tmp/feed-performance/replay/       本地冷热候选及并发回放
.tmp/feed-performance/lock-probe/   后台节流槽的受控竞争
```

复现命令：

```powershell
# 第一层采样；真实请求不会写生产数据库
.venv\Scripts\python.exe -m backend.tools.feed_performance --real --count 2 --output .tmp/feed-performance/real
.venv\Scripts\python.exe -m backend.tools.feed_performance --cache-only --output .tmp/feed-performance/cache-only
.venv\Scripts\python.exe -m backend.tools.feed_performance --lock-probe --output .tmp/feed-performance/lock-probe
.venv\Scripts\python.exe -m backend.tools.feed_performance --repeats 10

# 为正常本地服务开启第一层请求日志；不设置 DEEP
$env:BILIPERSONAL_FEED_PERF = '1'
.venv\Scripts\python.exe run.py
# 结束后移除当前 shell 的诊断开关
Remove-Item Env:BILIPERSONAL_FEED_PERF
```

## 测试结果

同步运行的全部 **73 项后端测试通过（259.363 秒）**，包括原 v0.3 30 项、v0.3.1 33 项、新诊断 10 项。诊断测试包含计数隔离、LRU／HTTP／重试区分、错误收尾、真实缓存分支、全局生成锁阻塞、节流 sleep／锁等待拆分、scheduler 非阻塞锁忙，以及深度统计开关和 SQL 时间口径。

第二层只在测试中校验实现正确性，没有用于本轮性能采样。没有前端代码变更，因此本轮不重复前端构建。诊断默认关闭；未提交代码。
