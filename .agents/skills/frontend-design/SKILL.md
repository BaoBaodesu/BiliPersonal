# Frontend Design

以资深视觉设计师的标准处理界面工作：让每个产品有符合其内容、受众和用途的视觉识别。避免套用通用模板；有依据地做出明确的配色、字体和布局选择。

## 从产品内容出发

先根据用户需求和代码库上下文确认产品主题、目标用户、页面任务与技术约束。尽量沿用仓库已经采用的框架、组件库和设计系统。用户没有给出某项信息时，先根据上下文作合理假设并继续；只有关键信息会实质改变设计结果时才提问。

设计应从产品主题中取材：行业、内容、真实工作流程和用户熟悉的视觉语言，决定页面应如何呈现。页面首屏应以最能说明产品或任务的内容开场，例如标题、图片、交互演示或关键操作。大数字、统计标签和渐变点缀不是默认答案。

## 设计原则

- 字体要服务产品个性和阅读层级。可以使用一个字体家族，也可以组合两个性格明确的字体；建立清楚的字号、字重和行距层级。正文行长通常控制在 80 字符以内，衬线字体可略长。
- 避免机械地突出标题中的单个词、全大写小标签和无实际作用的眉题。
- 边框、分隔线、编号、标签等结构元素必须表达真实的信息关系。只有内容确实有顺序时才使用编号。
- 动效应克制且有目的。页面自动播放的动效只在需要引导注意力时使用；响应用户操作的动效应明确表现状态变化。避免每个区块都统一淡入上移、每张卡片都配置相同悬停效果。
- 文案要帮助用户理解和操作。使用用户熟悉的名称、主动语态和明确动作；错误信息说明原因及修复方式，空状态提供下一步方向。

## 工作流程：构思、校准、实现、自查

### 1. 明确设计方向

动手改代码前，先依据用户需求和项目实际形成简短设计方案：

- **目的**：页面解决什么问题，谁会使用。
- **调性**：选择与产品匹配的明确方向，例如极简、编辑出版、工业工具、复古未来、自然有机或轻松活泼。
- **约束**：现有技术栈、设计系统、无障碍要求、性能要求及用户明确指定的样式。
- **识别点**：确定一个最值得记住的视觉或交互元素。
- **设计令牌**：定义 4–6 个有名称的颜色、字体及用途、间距层级和布局原则，并使用项目现有的令牌方式；没有现成规范时使用 CSS 自定义属性。

如能帮助比较布局，可用一两句文字或简易线框描述方案，不必为小范围改动输出冗长设计文档。

### 2. 检查是否落入通用模板

以下风格可以在合适的产品中使用，但不能不加判断地套用：

1. 暖米色底、高对比衬线标题与陶土色点缀。
2. 近黑底配单一荧光绿或朱红色。
3. 密集报纸栏、细分隔线和完全无圆角。
4. 所有内容都切成相同圆角卡片，配统一灰色阴影和装饰渐变。
5. 每个标题上方都放全大写眉题，数据一律用等宽字体，按钮或链接统一添加箭头。

如果方案只是因为常见而出现、与当前产品没有具体联系，就换成更贴近需求的处理。用户明确指定视觉方向时，以用户要求为准。把这个判断用于内部设计校准；只有解释设计决策确实有帮助时才向用户简述。

### 3. 实现界面

在现有技术栈中完成真实可用的页面或组件，维持项目既有编码习惯和设计系统。重点处理：

- 清楚的视觉层级和与内容匹配的空间构图；允许不对称或留白，但应有明确理由。
- 字体、颜色、尺寸和间距的一致性；优先复用项目令牌，避免散落的硬编码值。
- 与设计方向相符的背景、纹理和装饰；不为增加效果而堆叠渐变、噪声、阴影或自定义光标。
- 响应式布局、可见的键盘焦点、可读的色彩对比，以及对 `prefers-reduced-motion` 的尊重。
- 谨慎处理 CSS 选择器优先级，避免组件或区块样式互相覆盖。

不要仅为了设计建议擅自引入新依赖。React 项目只有在仓库已使用 Motion 库或用户要求时才使用它；否则优先采用现有方案或 CSS。

### 4. 自查并交付

依据用户要求和可用工具检查改动。若当前环境支持浏览器预览或截图，查看实际渲染并修正明显问题；若不支持，不要声称已完成视觉验证。检查是否有不服务内容的装饰、移动端布局问题、难以辨认的焦点状态、过度动效或不清楚的文案。

让一个重点成为页面的记忆点，其余部分保持有秩序。交付时简要说明主要改动和实际完成的验证。
